AnyWorld — technical notes

How the game is put together, for people who want to run, extend or connect it to their own AI. Source code: github.com/narve/any-world, under the PolyForm Noncommercial License 1.0.0 (free for noncommercial use; ask for commercial use).

What it is

A turn-based roguelike in the browser, seen from a tilted three-quarter angle. At the start of each run a large language model writes the whole game instance as one JSON document, the World Spec: genre, setting, stats and their names, rules, areas, actors, items and the win condition. During play the same model acts as a game master that may narrate, offer choices, spawn things or add rules, within strict limits.

Architecture

src/schema/   zod contracts: World Spec, GM actions, cross-reference checks
src/engine/   pure, deterministic rules (seeded RNG, no DOM, no clock)
src/llm/      providers, prompts, generate → validate → repair → balance, GM runtime
src/client/   three.js renderer, DOM UI, i18n (en, nb), touch input, audio
server/       Node backend: serves the client, POST /api/llm proxy (keys in env)
  • Engine: step(state, action) clones and returns a new state. The same seed and actions always give the same run, so bots can play thousands of runs and every bug report replays.
  • Renderer: low-poly models composed from archetypes and colours in the World Spec; no generated images. Quality tiers and instancing keep phones at a playable frame rate.
  • UI text: engine messages are keys with parameters, translated by the client catalog. World text is written by the model in the chosen language (meta.language).

How a world is made

  1. The prompt (or “surprise me”) goes to the model with a condensed schema description.
  2. The reply is parsed and validated with zod, then checked for broken references.
  3. Errors go back to the model for repair, a few times at most.
  4. Bots play the world in a Web Worker. If it is far too easy or too hard, the model gets the numbers and rebalances it.
  5. The finished world is kept in the browser and can be exported as a file and opened elsewhere. Imported files are treated as untrusted and validated again.

The game master

The GM is consulted at fixed moments (run start, new area, low health, boss seen, milestones, idle, death, victory) and returns only whitelisted actions. Each area has an action budget. Checks refuse actions that would win the run for the player, copy a boss, or stack harmful effects, and GM-invented rules are limited by the chosen difficulty. If the model is slow or fails, a built-in offline GM takes over and play never waits.

Without a usable AI, “Surprise me” plays one of the recorded demo worlds.

AI providers

Pluggable presets: Anthropic Claude, OpenAI, DeepSeek, Mistral, Qwen, Moonshot Kimi, Zhipu GLM, OpenRouter, Ollama, LM Studio, and any OpenAI-compatible endpoint. Several of them cannot be called from a browser (no CORS) and need the backend. A shared layer validates every structured answer against the schema and retries with error feedback, so models without native structured output also work. Small local models often struggle to write a whole world.

Testing

  • Unit tests (vitest) for schema, engine, providers and UI logic.
  • Bot simulation over every demo world: crashes, soft-locks and win-rate bands.
  • Playwright end-to-end in a real WebGL browser, desktop and emulated phones, English and Norwegian.

How it was built

The design was agreed with a human; then Claude agents built, reviewed, play-tested and fixed it in orchestrated workflows, with agents standing in for the LLM while writing the demo worlds. No live model was called during the build. The repository’s BUILD_LOG.md, STATS.md and RETROSPECTIVE.md describe the process and its limits.
